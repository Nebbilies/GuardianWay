# Phase 1.5 — Perimeter Hardening — Design Spec

**Date:** 2026-08-02
**Status:** Approved (design), pending implementation plan
**Feature:** Close out Phase 1 by hardening the perimeter — the layer that decides who gets in,
proves what they did, and reports whether the process actually works.

## Goal

Phase 1 delivered the management panels and the CI/CD pipeline. It did not deliver a trustworthy
perimeter. Phase 1.5 closes six specific gaps, each chosen because it is (a) a real defect, and
(b) demonstrable live.

Phase 2 (realtime GPS ingest + WebSocket gateway) sits on this same perimeter and is higher-volume
and less human-supervised than anything in Phase 1. Every gap below is cheaper to close now.

## Context that shaped the scope

Two facts about the deployment, established before designing:

1. **`k8s/` has no nginx and no Ingress.** Only ClusterIP Services for backend and frontend.
   Nothing is reachable from outside the cluster.
2. **`cd.yml` creates a kind cluster per push and destroys it.** There is no persistent
   environment, no TLS, no domain.

So there are two different proxy topologies — compose has one hop (nginx), k8s has zero — and any
control that presumes TLS or persistence is not applicable. This is the end state, not an interim
one.

**Optimization target:** a live defense with no written rubric. The selection criterion is
therefore not "is it correct?" but **"can you break it in front of an examiner and show the system
notice?"** Items with no demonstration are cut regardless of merit.

## Threat model

Six threats. Each has one control and one demo. This table is the spine of both the work and the
defense.

| # | Threat | STRIDE | State today | Control | Live demo |
|---|---|---|---|---|---|
| **T1** | Admin of School A reads School B's students/routes | Information disclosure | `$extends` scoping exists, **unproven** | Automated isolation suite | Run suite green, then live-curl B's `schoolId` → own rows only |
| **T2** | Credential stuffing on admin login | Spoofing | **nothing** | Dual-key rate limit (IP + account) on Redis, `auth.rate_limited` audit action | 20 bad logins → 429 → row appears in the audit UI |
| **T3** | "I didn't delete that school" | Repudiation | Audit exists, but `ip` records the **proxy's** address | `trust proxy` (hop count, never `true`) | Before/after curl through nginx; IP changes |
| **T4** | Broken deploy reported healthy | DoS / availability | Probe hits static `/` | `/healthz` + `/readyz`, wired to compose + k8s + CD | `docker compose stop postgres` → 503, container flips unhealthy |
| **T5** | Route mounted without its guard | Elevation of privilege | Per-route `authorize()`, **unproven** | RBAC matrix test | role × route table in test output |
| **T6** | Clickjacking / XSS on the portal | Tampering | No headers | helmet + nginx headers | `curl -I` |

> **Supersession note (post-implementation):** the "helmet + nginx headers" control for T6 changed
> shape during implementation — nginx ended up emitting none of the security headers. See the T6
> section below for what shipped and why.

**T3 evidence** (observed in the live dev database):

```
auth.login|::ffff:172.18.0.6|curl/8.12.1     <- 172.18.0.6 is the nginx container
school.created|::ffff:172.18.0.1|curl/8.12.1
```

Every row behind the proxy is attributed to the same internal address. The audit log's `ip` column
currently cannot answer the one question it exists to answer.

**T5 evidence** is a real incident in this repository's history: `/api/schools` was mounted without
`tenantContext`, producing audit rows with no actor at all. "We found this class of bug and here is
the test that now catches it" is a materially stronger position than "we have RBAC."

## Decisions (locked)

- **Rate-limit store is Redis, not in-memory.** At `replicas: 1` an in-memory store is functionally
  identical and simpler. Redis is chosen anyway because it is currently in the stack and entirely
  unused — `config/redis.ts` connects and nothing imports it — so "why is Redis here?" has no
  present-tense answer today. This gives it one, is the correct production pattern, and adds a demo
  beat (restart the backend, the limit survives).
- **The rate limiter fails *closed* on auth routes when Redis is unavailable.** The usual choice is
  fail-open (availability beats marginal security), but here it is coherent with T4: if Redis is
  down, `/readyz` already reports NotReady and the replica leaves rotation, so failing closed
  strands nobody who was not already cut off.
- **Liveness probes never check dependencies.** Readiness does. See T4 below.
- **Integration tests authenticate through the real `POST /api/auth/login`**, not hand-minted JWTs.
  A hand-minted token skips the middleware chain that is the subject of the test.
- **Cross-tenant reads by id return 404, not 403.** A 403 confirms the row exists.
- **CSP ships report-only.** Enforcing against the Next.js App Router requires either nonce wiring
  or `unsafe-inline`; a CSP weakened until the app loads is theatre.

## Out of scope (deliberate, with the defense answer)

Cutting these is part of the deliverable. Each has a prepared one-line answer.

| Cut | Answer if asked |
|---|---|
| HSTS | No TLS anywhere in the topology — asserting it would be a false claim |
| Backup CronJob | The cluster is created and destroyed per push and the DB is seeded per run. Documented as design-only |
| Graceful shutdown | Real gap, but there is no persistent traffic to drain and nothing to demonstrate |
| Soft-delete/restore parity for `Bus`/`BusRoute`/`BusStop`/`BusTrip` | Product consistency, not a security control. Backlogged |
| Password self-service (forgot/change) | "Another admin re-issues the invite" is a sufficient recovery path at this scale |
| Enforced CSP | Report-only ships; enforcing needs nonce wiring. "We measured before enforcing" |
| Row-Level Security | App-layer scoping plus the T1 suite is adequate. Revisit when Phase 2's ingest path introduces raw SQL that bypasses the `$extends` |

**Stretch, only if time allows:** validating the inbound `x-request-id` header. `requestContext`
currently adopts it verbatim, so a client can choose its own audit `traceId` — colliding it with a
legitimate request to muddy an investigation, or injecting control characters into log lines. It
does demonstrate (`curl -H 'x-request-id: evil<newline>FAKE LOG LINE'`), but it is marginal beside
the six above.

## T3 — Trust the proxy

`app.set("trust proxy", hops)` in `app.ts`, **before** `requestContext` — which runs before
anything that reads `req.ip`.

Value from env `TRUST_PROXY_HOPS`, parsed as an integer, **default `0`**:

| Environment | Hops | Why |
|---|---|---|
| compose | `1` | nginx is the only proxy |
| k8s | `0` | no nginx, no Ingress — the backend Service is hit directly |
| local `npm run dev` | `0` | no proxy |

Set in three places: `backend/.env` (local), the backend service environment in
`docker-compose.yml`, and `k8s/secret.yaml`. An unset variable falls back to `0`, which fails safe
— `req.ip` becomes the socket peer, which is wrong but not forgeable.

**Never `true`.** That trusts any client-supplied `X-Forwarded-For`, letting an attacker forge
their own audit IP *and* evade T2's per-IP limit. A hop count means Express reads the *nth entry
from the right*, which only nginx controls.

nginx already sets `X-Real-IP` and appends `X-Forwarded-For`; no nginx change is required for this
control.

**Known residual, documented rather than fixed:** `docker-compose.yml` also publishes backend
`8000:8000` directly. A client hitting `:8000` with a forged `X-Forwarded-For` while `hops=1`
controls `req.ip`. That port is a development convenience. Volunteering this in a defense is
stronger than being caught on it.

**Done when:** a request through `:8080` writes an audit row containing the host's address rather
than `172.18.0.x`, and the direct-to-`:8000` and through-nginx paths now differ correctly instead
of both being wrong.

## T6 — Security headers

> **Supersession note (post-implementation):** the plan below has nginx emit the HTML/static
> headers. That did not ship. `nginx.conf` sets no security headers at all; helmet emits them for
> API responses (as planned) and `frontend/next.config.ts` emits them for HTML and static
> responses instead of nginx. This was a deliberate change, not drift: it means one source owns
> each response class, and the headers still apply in the k8s topology, which has no nginx or
> Ingress in the request path — an nginx-owned header would simply vanish there. The rest of this
> section is left as originally written for the record.

**Backend:** `helmet()` mounted before routes. `strictTransportSecurity` disabled — there is no TLS
and asserting HSTS would be false. CSP disabled at this layer; the backend serves only JSON.

**nginx:** headers on HTML responses, declared in the `server` block:

- `X-Frame-Options: DENY`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Content-Security-Policy-Report-Only` — starting policy:
  `default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; script-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`

  `style-src 'unsafe-inline'` is present because Next.js injects inline styles; it is recorded here
  as a known weakening rather than discovered later. Report-only means nothing breaks either way —
  the point of this commit is to *measure* what the policy would block.

Cookies are already `httpOnly` + `sameSite: lax`, which is the important half; the missing half is
that the portal can be framed (clickjacking an admin into a destructive click) and has no CSP to
blunt an XSS.

**Footgun to document in the config:** nginx `add_header` does not inherit into a `location` block
that declares its own `add_header`. The `/_next/static/` block currently declares none, so
`server`-level directives apply today — but adding one there later would silently drop all four
headers for static assets.

> **Supersession note:** moot as shipped — nginx carries no `add_header` directives for these
> headers at all (see the note at the top of this section), so there is no `server`-level default
> for a `location` block to accidentally shadow.

## T2 — Login rate limiting

Libraries (verified compatible against the current tree — Express 5.2.1):
`express-rate-limit@^8.6.1`, `rate-limit-redis@^6.0.0` (peer: `express-rate-limit >= 8.6.0`).

Two limiters on `POST /api/auth/login`:

| Limiter | Key | Budget | Counts |
|---|---|---|---|
| per-IP | `rl:ip:<req.ip>` | 20 / 15 min | all requests |
| per-account | `rl:acct:<sha256(email)>` | 5 / 15 min | failures only (`skipSuccessfulRequests`) |

Per-IP alone is defeated by a botnet; per-account alone lets a single host enumerate many accounts.
Both are required.

**The email is SHA-256'd into the key** so Redis holds no plaintext PII.

`POST /refresh` and `POST /setup-password` each get their **own** per-IP limiter instance with a
distinct key prefix (`rl:ip:refresh:`, `rl:ip:setup:`) — not the login limiter reused. A shared
counter would let failed logins exhaust a legitimate user's refresh budget, turning the control
into a self-inflicted denial of service. Both are credential exchanges, and `setup-password`
consumes a token that is guessable in principle.

- **Response:** `429` with `Retry-After`. The frontend login form surfaces it rather than showing a
  generic error.
- **Audit:** new action `auth.rate_limited` added to the union in `utils/audit.actions.ts`, with
  metadata `{ reason: "ip" | "account" }`. This is what makes the demo land — the block appears in
  the audit viewer UI already built in Phase 1. Writes stay best-effort per the existing
  `auditService.record` contract.
- **Fail closed:** a guard ahead of the limiters checks `redisClient.isReady`; not ready on an auth
  route → `503`.

**Lockout policy:** rate limiting only, no sticky account lock. A sticky lock is stronger but
becomes a denial-of-service vector against a known admin email, and there is no unlock path
(password self-service is out of scope).

## T4 — Health and readiness

Both endpoints registered **before** `pinoHttp` and `metricsMiddleware`, next to the existing
`/metrics` route — probe traffic must not flood the logs or skew request metrics.

```
GET /healthz  → 200 always. No dependency checks.
GET /readyz   → Postgres SELECT 1 ‖ Redis PING, in parallel, ~1s timeout each
                200 {status:"ok",   checks:{db:"ok",   redis:"ok"}}
                503 {status:"fail", checks:{db:"fail", redis:"ok"}}
```

The status code is for the orchestrator; the body is for humans.

Timeouts are enforced with `Promise.race` — a *hung* dependency must fail the probe rather than
hang it. `config/redis.ts` calls `connect()` at import with no await and no retry gate, so a Redis
outage at boot leaves a client that never connects; `/readyz` therefore reads the client's actual
`isReady` state instead of assuming the import succeeded.

### Why liveness must not check dependencies

| Probe | Question | Failure action | Checks dependencies? |
|---|---|---|---|
| liveness | "is this process wedged?" | **restart the pod** | **No** |
| readiness | "can this replica serve traffic right now?" | **remove from the load balancer** | **Yes** |

Checking the database in a liveness probe is an outage amplifier: the DB blips, every replica fails
liveness, Kubernetes restarts the whole fleet at once, and the restart storm prevents the DB from
recovering. This is the most important idea in the workstream and the most likely to be probed.

### Four consumers — all four required

| File | Change |
|---|---|
| `k8s/backend.yaml` | readiness → `/readyz` (period 5s, failureThreshold 3); **add** liveness → `/healthz` (period 20s, failureThreshold 3, initialDelaySeconds 15) |
| `k8s/frontend.yaml` | add liveness → `/` alongside the existing readiness probe |
| `docker-compose.yml` | **add** a backend healthcheck → `/readyz` (none exists today) |
| `.github/workflows/cd.yml` | smoke test curls `/readyz`, not `/` |

The last row is the point of the workstream: today, a deploy that cannot reach its database passes
CI green, because both the readiness probe and the smoke test hit `/`, which returns the string
`"Hello, api is on!"` without touching Postgres or Redis.

## T1 / T5 — Integration test harness

Six test files exist today, all unit-level. Nothing exercises a real HTTP request against a real
database. `supertest` is already in `devDependencies` and unused — the intent was there.

The untested invariant is the important one: the Prisma `$extends` in `config/tenant-db.ts` is the
only thing preventing cross-school data leakage. A refactor that drops a model from
`SCOPED_MODELS`, or a repository that reaches for `basePrisma` directly, leaks silently — no error,
no failing test.

### Layout

```
backend/
  test/integration/
    setup.ts                          container + migrate + fixture seed
    fixtures.ts                       School A/B, an ADMIN each, a PARENT, a SUPER_ADMIN,
                                      plus one row per scoped model per school
    helpers/login.ts                  real POST /api/auth/login → cookie jar
    isolation.integration.test.ts
    rbac.integration.test.ts
  vitest.integration.config.ts
```

### Harness decisions

- **Testcontainers** (`@testcontainers/postgresql@^12.0.4`) with image
  `timescale/timescaledb-ha:pg17` — must match compose, because the PostGIS geography columns and
  the Timescale hypertable are load-bearing in the migrations. One container per run;
  `prisma migrate deploy` applied once.
- **Reset:** truncate and reseed per test file. Deterministic; the added runtime is acceptable.
- **`singleThread`** — one shared database.
- Separate vitest config so `npm run test` stays fast; new `test:integration` script.
- Testcontainers startup failure must surface as a clear error, never a silent skip.

### T1 — Isolation cases

Run per scoped model (`Bus`, `BusRoute`, `BusStop`, `BusTrip`, `StudentProfile`, `AuditLog`):

1. Admin A lists → only School A rows
2. Admin A fetches a School B row by id → **404** (not 403 — 403 confirms existence)
3. Admin A sends `?schoolId=<B>` → still only A's rows *(verified by hand in a previous session;
   this makes it a permanent test)*
4. Admin A creates with a forged `schoolId: B` in the body → the row lands in A
5. SUPER_ADMIN (null school) → sees all

### T5 — RBAC matrix

Table-driven over every mounted route and method in `app.ts` × `{unauthenticated, PARENT, DRIVER,
ADMIN, SUPER_ADMIN}`, asserting `401` / `403` / `2xx`. Cheap once the harness exists, and it catches
exactly the failure mode that hit `/api/schools`: adding a route and forgetting a middleware in the
chain.

### CI

A new `integration` job in `ci.yml`, kept separate from the existing `test` job so fast feedback
stays fast. GitHub runners ship Docker, so Testcontainers runs unmodified.

## Exit criteria

Phase 1 is closeable when all six hold:

1. An audit row records the client's IP, not the reverse proxy's. *(T3)*
2. `curl -I` on the portal returns frame, nosniff, referrer, and CSP-report-only headers. *(T6)*
3. A password-guessing loop against `/api/auth/login` is throttled, and the block appears as an
   `auth.rate_limited` row in the audit viewer. *(T2)*
4. A backend with an unreachable database reports 503 on `/readyz`, goes unhealthy in compose,
   NotReady in k8s, and **fails the CD smoke test**. *(T4)*

   > **Supersession note (post-implementation):** the smoke test is not what catches this in CD.
   > `rollout status` in `.github/workflows/cd.yml` blocks on the same `/readyz`-gated pod
   > readiness and times out **before** the smoke-test step runs, so `rollout status` is the actual
   > gate; the smoke test is a secondary check that a broken-dependency deploy never reaches.
   > `docs/demo-script.md` already states this correctly — this spec did not.
5. An automated test proves School A's admin cannot read School B's rows — including with a forged
   `schoolId` — and it runs in CI. *(T1)*
6. A role × route matrix test asserts every mounted route's guards, and it runs in CI. *(T5)*

## Sequencing

Dependencies are real: T3 gates T2 (a rate limiter keyed on an untrusted `req.ip` throttles every
user as one client), and the harness gates both test suites.

| # | Commit | Threat |
|---|---|---|
| 1 | `trust proxy` + env wiring | T3 |
| 2 | helmet + nginx headers | T6 |
| 3 | Redis-backed dual rate limiter + `auth.rate_limited` action + frontend 429 handling | T2 |
| 4 | `/healthz` + `/readyz` | T4 |
| 5 | Probes wired into k8s, compose, and the CD smoke test | T4 |
| 6 | Integration harness (container, fixtures, login helper, vitest config) | T1/T5 |
| 7 | Isolation suite | T1 |
| 8 | RBAC matrix + `integration` CI job | T5 |
| 9 | `docs/demo-script.md` | all |

Commits 1–9 are the close-out set. Rough weighting: T2+T3+T6 ≈ one third, T4 ≈ one quarter, the
harness and suites ≈ the remainder. The harness is the largest single chunk because it is new
ground, and it is also the piece that keeps paying out through Phase 2.
